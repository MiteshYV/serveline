## order-number-day-boundary-tz · HIGH

**Where** `src/db/repos/dashboard.ts:88`  
**What** `orderNumbers` buckets orders into IST calendar days with `(placed_at + interval '330 minutes')::date`, but casting a `timestamptz` to `date` uses the database session's TimeZone, which is not UTC. PGlite initdb's the session TimeZone from the host's UTC offset rounded to whole hours, so on an IST machine it is `Etc/GMT-5` (UTC+5) — including the repository's own `./data/serveline.pglite`. The `+330 minutes` then stacks on top of that, giving an effective offset of UTC+10:30 and a day boundary at 19:00 IST instead of midnight.  

**Consequence** The counter board's order numbers — the number the kitchen shouts across the counter, rendered as `#{order.number}` in `src/ui/OrderCard.tsx:176` — restart at #1 at 7pm, in the middle of dinner service. Two orders live on the board at the same moment both show `#1`, two more both show `#2`, and staff hand the wrong bag to the wrong customer. The Done group on the same page is cut at true IST midnight (`istDateStart(istDate(now))` in `app/(restaurant)/app/(shell)/page.tsx:34`), so the list and the numbering disagree about what "today" is. Nothing in the 289-test suite covers `orderNumbers`.

**Verified** Real and reproduced through the repository's own `orderNumbers`. `placed_at` is `timestamptz`, so `(placed_at + interval '330 minutes')::date` is resolved through the PGlite session TimeZone, which initdb sets from the host offset (`Etc/GMT-5` on this IST machine, with TZ unset). The +5h session offset stacks on the +5:30 literal, moving the IST "day" boundary to 19:00, and two live board orders then both render `#1`. No ADR covers it, no test asserts it, and it contradicts the function's own docstring ("#1 is the first order after midnight").

**Fix** In `src/db/repos/dashboard.ts:88`, pin the bucket expression to UTC so it cannot depend on the session TimeZone:

  partition by (((${order.placedAt} at time zone 'UTC') + interval '330 minutes')::date)

`timestamptz at time zone 'UTC'` yields a plain `timestamp`, and casting that to `date` is TZ-independent — verified identical under `Etc/GMT-5`, `Etc/GMT0` and `America/New_York`. The window bound on the line below (`istDayStart(earliest)`) is already correct and needs no change.

Add a regression test (there is no `dashboard.test.ts` yet; follow the fixture pattern in `src/db/repos/commerce.test.ts`) inserting orders either side of 19:00 IST on one IST day plus one just after true IST midnight, asserting #1..#n run unbroken through the evening and restart only at midnight. The test must not set `TZ`, or it will mask the bug — the failing case only appears when the host offset is non-zero.

## voice-place-order-not-idempotent · HIGH

**Where** `src/voice/tools.ts:310`  
**What** The `place_order` tool has no guard against being called twice in one call: it does not check whether this session has already placed an order and it never clears `session.cart`. Nothing in `src/voice/prompt.ts` forbids a second call either (the only rule is the read-back, prompt.ts:119).  

**Consequence** One phone call produces two identical orders. The kitchen cooks the food twice, the caller receives four SMS messages (two "order received" and two "pay Rs 90" links, both live), and two payment links for the same food are outstanding at the gateway. The `call` row records only the second order id, so the first duplicate is not visible from the call review screen — only on the board as an unexplained twin. Any real model that re-issues the tool after a timeout, a repeated caller confirmation ("sorry, did that go through?"), or a dropped tool result triggers it; the scripted mock hides this because its `cartOpen` policy (src/adapters/llm/mock.ts) happens never to ask twice.

**Verified** Real and reproduced: `place_order` (src/voice/tools.ts:310) has no guard and the loop has none either, so two calls in one voice session create two paid-for orders, two live payment links and four SMS. Nothing in CLAUDE.md, the Build Spec, the ADRs or the tests sanctions this — the only relevant note (loop.ts:460) merely records that the cart is not cleared, it does not defer idempotency.

**Fix** The proposed session guard is right but not sufficient on its own; do both layers.

1. Session guard (stops the common case). Add `orderId: string | null` to `Session` (src/voice/session.ts, initialised to null in `createSession`). At the top of `place_order`, after arg validation and before the cart check:
   `if (session.orderId) return ok({ orderId: session.orderId, already: true, ...the same shape as a fresh success })`
   and on success set `session.orderId = order.id`, `session.cart = []`, `session.codeText = null`. Set it only on success, so the consent-detour retry (loop.test.ts:148) still works. Clearing the cart makes the stale comment at src/voice/loop.ts:460-462 wrong — update it; the `!state.orderId` condition already carries the intent, so `parkOrder` behaviour is unchanged.

2. Durable guard (the layer the session cannot provide). The in-process Map dies with the process and does not exist on the web path, so add idempotency inside `placeOrder` itself: take an optional idempotency key (`context.callId` for calls, a form-issued token for the page) and either a partial unique index on `order(call_id)` for non-cancelled rows, or a lookup-before-create that returns the existing order. Without this, `placeOrderAction` (app/(customer)/r/[slug]/checkout/actions.ts:181) still duplicates on a retried submit after a network timeout, and a voice session that outlives a dev-server reload still duplicates too.

3. While in there, `place_order` should refuse rather than duplicate if an `awaiting` payment link already exists for the same call — the same hazard the M1 review logged as finding 13 (docs/reviews/2026-09-20-m1-review.md:39) for the staff "resend payment link" button: two live 30-minute links, both payable, no cancel path.

## consent-recorded-without-an-answer · HIGH

**Where** `src/voice/loop.ts:355`  
**What** `session.noticeRead` is set from `response.text` *before* the same response's tool calls are executed, so one model response can both read the consent notice aloud and call `record_consent{agreed:true}`. The caller is never given a turn in which to answer.  

**Consequence** A DPDP `consent_record` is written with `channel: 'call'` and `evidence: { callId, rendering: 'spoken' }` for a caller who was never asked and never said yes — and the transcript on the review screen proves they never did. The record then unlocks `place_order`, so a profile row is written on their behalf too. ADR 0005 makes this gate the guarantee behind the prompt's manners ("Consent recorded without the notice is not consent"); it does not survive a model that batches text with a tool call, which Gemini routinely does.

**Verified** Real and reproduced: loop.ts sets session.noticeRead from response.text before executing that same response's tool calls, so one model response reads the consent notice and records consent in the same breath, writing a DPDP consent_record and unlocking place_order for a caller who never answered. Not covered by ADR 0005 (which makes this gate the guarantee), not an artifact of the mock adapter, and not asserted by any existing test.

**Fix** Require that the notice went out in a strictly earlier turn than the record_consent call. The claimed fix's shape is right but its mechanics are wrong: `state.seq` is not reachable from a tool handler (tools get `session`, not `CallState`), and moving the assignment to the end of `takeTurn` is unnecessary — a strict comparison suffices.

Use the per-turn counter that already exists. `session.turnCount` is incremented once in `takeTurn` before `respond()` (src/voice/loop.ts, just after checkBeforeModel), so during turn N it equals N.

1. src/voice/session.ts: replace `noticeRead: boolean` with `noticeReadAtTurn?: number` (init undefined at line ~72).
2. src/voice/loop.ts:355 — at the same detection site, `if (session.noticeReadAtTurn === undefined && noticeWasRead(response.text, session.lang, state.deps.restaurant.name)) session.noticeReadAtTurn = session.turnCount`.
3. src/voice/tools.ts:297 — `if (session.noticeReadAtTurn === undefined || session.noticeReadAtTurn >= session.turnCount) return refuse('notice_not_read')`.

Within the turn that reads the notice, noticeReadAtTurn === turnCount, so the batched record_consent is refused and the model is told `notice_not_read`; on the caller's next turn turnCount is larger and the yes records. Also update src/voice/tools.test.ts:321 and :334, which set `s.noticeRead = true` directly, to set `s.noticeReadAtTurn` to a value below `s.turnCount`, and tools.test.ts:317's refusal case stays as is.

## place-order-not-idempotent-per-call · HIGH

**Where** `src/voice/tools.ts:310`  
**What** `place_order` has no per-call guard: nothing stops the model calling it twice in one call, and `session.cart` is never cleared after a successful placement, so a second call creates a second, complete order.  

**Consequence** A caller who changes their mind after the assistant has already placed the order ("actually, cash instead", "make it delivery") gets two real orders. The kitchen sees two tickets for the same food, the customer receives an order-confirm SMS for each plus a UPI payment link for the first, and `call.order_id` points only at the second — so the first order is orphaned from the call that made it and nobody reviewing the call can see it. On a paid channel this is a double charge.

**Verified** Real and reproduced end to end through the actual loop: two successful `place_order` calls in one call create two complete, live orders, two `order_confirm` SMS and a payment link, and the `call` row links only the second. Nothing in the Build Spec, the ADRs, the M2 design or the existing tests sanctions it — the only thing standing against a second placement is a prompt line (`src/voice/prompt.ts:126`), and `loop.ts` `close()` already assumes the invariant the code does not enforce.

**Fix** The claimed fix is right; two details matter.

1. Add `orderId: string | null` to `Session` (`src/voice/session.ts`), initialised null in `createSession`.
2. In `place_order` (`src/voice/tools.ts:310`), first line: `if (session.orderId) return refuse('order_already_placed', { orderId: session.orderId })`. Set it **only on a successful `placeOrder`** — after the `if (!result.ok) return refuse(...)` line — never on a refusal. This is load-bearing: the consent flow deliberately refuses `consent_required`, reads the notice, then retries `place_order` (`src/adapters/llm/mock.ts` `record_consent` branch, and `tools.test.ts:249-257` retries after `empty_cart`/`address_required`), and an eager set would break both.
3. Clear `session.cart = []` (and `session.codeText = null`) at the same point, so a stale cart cannot be re-placed and cannot be parked.
4. Add `order_already_placed` to the refusal vocabulary the prompt explains, so the model says "that order is already in, let me put you through" rather than inventing a recovery; `src/voice/prompt.ts:126` already routes a change to `transfer_to_human`.
5. `loop.ts` needs no change beyond consistency: `close()`'s `!state.orderId` guard and `note()`'s assignment then agree with a structural invariant instead of a prompt instruction. Optionally make `note()`'s `case 'place_order'` a `state.orderId ??=` so the first placement stays the linked one.

Worth a regression test in `src/voice/tools.test.ts`: place once, then assert the second `place_order` on the same session is `{ ok: false, reason: 'order_already_placed' }` and that `repos` still holds exactly one order for that call.

One severity nuance, in the claim's favour rather than against it: the reproduced run only charged once because I made the second `cod`. Two `upi_link` placements produce two live payment links for the same food, which is the ₹240-twice case and has no cancel path (the same gap as finding 13 in docs/reviews/2026-09-20-m1-review.md). High is correct.

## direct-order-share-divides-month-by-partial-weeks · HIGH

**Where** `app/(restaurant)/app/(shell)/today/page.tsx:45`  
**What** Direct Order Share puts a whole month of delivered orders over only those aggregator weeks whose Monday falls inside the same month. Build Spec §12 says "divided by (those plus `external_order_count` for the same weeks)" — the numerator and denominator here cover different spans, and the denominator lags the numerator by up to 13 days.  

**Consequence** The owner's North Star number on /app/today is systematically overstated, and for roughly the first week of every month it reads 100% even when the restaurant is getting half its orders from Swiggy and Zomato — because no Monday has fallen in the new month yet, so the denominator is zero. `share()` only returns null when direct+external is 0, so the "needs last week's counts" hint never fires and nothing warns the owner. A pilot restaurant judged against Ideation §9's "30% Direct Order Share in 60 days" would be scored on a number that cannot be right.

**Verified** Real, and worse than the claim states. `/app/today` divides a month-to-date count of delivered orders by aggregator counts for only those weeks whose Monday falls inside the same month, so the two sides of the ratio cover different spans and the denominator lags the numerator by up to 11 days. Nothing in `docs/adr/`, the M1 review, or any test covers or accepts this; Build Spec §12 explicitly says "for the same weeks".

**Fix** Make both sides cover the same weeks, in the repo layer rather than the page (CLAUDE.md: "app/ — routes only. Thin.").

1. Replace `externalOrdersBetween` with a function that returns the entered weeks themselves, e.g. `externalWeeksBetween(outletId, fromDate, toDate): Promise<{ weekStart: IsoDate; orders: number }[]>` selecting `week_start` and `swiggy+zomato+other`. Widen the window so a week overlapping the month boundary is not silently dropped: pass `addDays(istDate(monthStart), -6)` as `fromDate` and keep only weeks that overlap [monthStart, now).

2. Add a repo `directOrderShare(outletId, from, to)` that takes those weeks, builds the instant span for each (`istDateStart(weekStart)` to `istDateStart(addDays(weekStart, 7))`, clamped to `now`), counts delivered orders over exactly that union (a single SQL count with an OR of ranges, or a join against the week rows), and returns `{ direct, external }`. Gaps from "Skip this week" then drop out of both sides instead of only the denominator. The page keeps `share(direct, external)` and does no arithmetic of its own.

3. Change `share()` at page.tsx:21-22 to `direct + external === 0 || external === 0 ? null : ...` so the existing hint at line 92 ("needs last week's Swiggy and Zomato counts") fires instead of the page printing 100%. This alone is the minimum patch and is worth landing even before step 2, because it removes the 11-day 100% window.

4. Apply the same treatment to `shareLast` (page.tsx:44/46), and label the tile with the period actually measured (e.g. "weeks of 7-20 Sept") so the owner can see the number is week-aligned, not month-to-date.

5. Add a regression test alongside src/db/repos/catalog.test.ts: 10 direct + 10 aggregator per day with every Monday answered must read 50% on any day of the month, including the 1st.

## refused-code-blocks-order · HIGH

**Where** `src/checkout/place-order.ts:147`  
**What** Once a discount code in the URL is refused (already redeemed, expired, limit reached), `placeOrder` returns `code_refused` instead of pricing the order without the discount, so no order can ever be placed from that URL — and the checkout's retry path re-sends the same `c=` and gets the same refusal forever.  

**Consequence** A returning customer who scans their Direct Order Card a second time — the exact win-back loop Ideation §7 and §8 flow 5 are built on — reaches a checkout that says "A card from this restaurant has already been used with this number, so the menu is shown without the discount", taps "Place order", and nothing happens. Ever. The restaurant never sees the order and never learns it was lost. The same trap catches every customer holding a link to an expired promo code. Build Spec §6 line 298 says the opposite: "A second attempt shows the menu without the discount and says so" — the *redemption* is refused, not the order.

**Verified** Real and reproduced: with `c=WELCOME10` in the URL, `placeOrder` returns `code_refused` on every attempt after the first redemption, and the checkout's retry path re-sends the identical `qs`, so the order can never be placed from that URL; dropping `c=` places the same cart immediately. Build Spec §6 line 298 ("A second attempt shows the menu without the discount and says so") requires the refusal to be of the redemption, not of the order, and no ADR covers this.

**Fix** Fix on the caller side, not in placeOrder. The claim's "belt and braces" suggestion (set `codeOutcome = null` and return `ok: true`) must NOT be applied as written: src/checkout/place-order.test.ts:155-156 deliberately asserts that a second redemption returns `reason: 'code_refused'` with `code.reason === 'already_redeemed'` (Build Spec §14 M1 criterion), and that server-side guard is what protects the lost-race cancellation at place-order.ts:183-188.

1. app/(customer)/r/[slug]/checkout/page.tsx: after resolving `code` (line 155-158), derive an effective query string for the confirm step — when `code && !code.ok`, use `contextQuery({ kind: 'delivery' })` (i.e. '') instead of `qs` — and pass that to `ConfirmStep`'s `qs`, to `menuHref` and to `changeAddressHref`. The `code` prop still goes through, so the Band at ConfirmStep.tsx:164 keeps explaining the refusal, but the next submit and the "Back to menu"/"Change" links carry no code and price at full.
2. app/(customer)/r/[slug]/checkout/ConfirmStep.tsx: hold `qs` in state (`const [query, setQuery] = useState(qs)`), submit `query`, and in the `code_refused` branch (line 106) also `setQuery(q => new URLSearchParams(q) minus 'c')` before returning. This covers the refusal that can only arrive from the server — the lost-race path at place-order.ts:183-188, where the code was live at page render and was redeemed by another tab in between — so the customer's immediate second tap goes through at full price instead of looping.
No change is needed to `parseContext`/`contextQuery` (lib.ts:37-46); an empty `qs` already round-trips correctly through `withQuery` and `placeOrderAction`.

## unpriceable-cart-line-kills-cart · HIGH

**Where** `app/(customer)/r/[slug]/cart.ts:73`  
**What** `prune` validates that a saved cart line's item, variant and option ids still exist, but not that the line still satisfies each option group's `minSelect`/`maxSelect`. A line that breaks those makes `priceCart` throw; both MenuClient (:97-103) and ConfirmStep (:70-77) swallow that throw into `cart = null`, which silently hides the cart bar and renders "Your cart is empty" while the cart is still in localStorage.  

**Consequence** A restaurant edits an item's option group on the dashboard — makes "Served with" required, or lowers a group's maximum — which is an ordinary menu edit (app/(restaurant)/app/(shell)/menu/actions.ts:103-107 keeps the group id, so the line survives `prune`). Every customer with that item in a saved cart then opens the ordering page, sees their dishes listed with quantities against them, and there is no cart bar, no error, and no way to reach checkout. Going to /r/{slug}/checkout says "Your cart is empty". "Back to menu" returns to the same screen. The cart is never cleared, so the state survives reloads and sessions indefinitely; the diner has to guess which dish to remove, or give up. The restaurant loses the order and sees nothing.

**Verified** Reproduced exactly as described in a live browser on the seeded demo restaurant: a cart line that satisfies `prune` but violates an option group's `minSelect` makes `priceCart` throw, both surfaces swallow it into `cart = null`, and the diner gets a menu with quantities but no cart bar and a checkout that says "Your cart is empty" while the cart stays in localStorage. No ADR covers it, no test asserts the swallow, and the trigger is an ordinary dashboard menu edit because the item form submits the group and option ids as hidden fields, so `syncOptionGroups` preserves them and the stale line survives `prune`.

**Fix** Make `prune` in app/(customer)/r/[slug]/cart.ts:73-82 the single authority on "can this line still be priced": after the id checks, run each surviving line through `priceCart([line], [item])` inside try/catch and drop the ones that throw, exactly as it already drops lines whose ids no longer resolve. Then make the drop visible: have MenuClient (useEffect at :52-54) and ConfirmStep (useEffect at :66-68) compare the pruned line count with the loaded one and render the existing `checkout.itemUnavailable` string when lines were removed, saving the pruned array back so the dead row does not persist. As a floor, MenuClient.tsx:182 must never render items with no cart bar: if `priceCart` still throws, show the error (CART_ERROR_KEY already maps min_select to 'menu.required') plus a "clear cart" action rather than nothing.

**What** `requirePlatform()` and `requireStaff()` trust the `role` and `sub` claims in the JWT and never look the user up. Nothing confirms the `platform_user` / `staff_user` row still exists or still holds that role, and there is no revocation list — signing out only deletes the cookie on that one device.  

**Consequence** An agent who leaves, or a counter staff member the owner removes, keeps full access for up to the token's 7-day life from any device where the cookie was already set, including the admin-only audit log which shows every restaurant's write history. An owner demoted to `staff` keeps owner-only powers (settings, card batches, billing) until their cookie expires. There is no way for anyone to cut a session short.

**Verified** Real and reproduced: authorisation is decided entirely from the JWT claims, with no read of `platform_user`/`staff_user`, so a cookie for a row that no longer exists (or whose role has changed) still passes — and the admin-only audit log rendered for a subject id that is not a platform_user. Nothing in the Build Spec, the ADRs, the two review deferral lists or the tests sanctions it; CLAUDE.md's "stateless by design at M1" line is explicitly scoped to the OTP challenge ("the OTP lives in a signed challenge, not a table"), not to authorisation.

**Fix** Right in direction, wrong in two details.

1. The by-id lookups are NOT already in the repos. src/db/repos/staff.ts has only `findStaffByPhoneHash` and `findPlatformUserByPhoneHash` (both by `phone_hash`, for login). Add `findStaffUserById(id)` and `findPlatformUserById(id)` there and export them from src/db/repos/index.ts.

2. "one query per request at most" is wrong for the platform side. `currentOutlet()`'s `cache()` wraps `getRestaurant`, not `requireStaff`; and `requirePlatform()` is called by app/(platform)/agent/(console)/layout.tsx:15 AND again by every page and server action (25 call sites), because a layout does not re-render on client navigation. So wrap the lookup itself: in src/auth/session.ts define `const loadStaff = cache(findStaffUserById)` / `const loadPlatform = cache(findPlatformUserById)` (React `cache`, per-request) and call those from `requireStaff`/`requirePlatform`. That keeps it to one query per request per audience.

Then: treat a missing row as signed out (`redirect('/app/login')` / `redirect('/agent/login')`) and take `role` — and, for staff, `restaurantId` — from the row rather than the claim, so a demotion takes effect on the next request. Keep src/auth/jwt.ts DB-free; it is deliberately importable under plain `node --test`. Worth a `docs/adr/` note or a spec line, since it is the first DB read in the auth layer.

Severity medium is right. Not high: it is not a forgery path (a real attacker needs a legitimately issued cookie; minting one needs SESSION_SECRET, which is the separate secrets.ts dev-fallback finding), and at M1 there is no in-app way to delete or demote a staff/platform user — no repo function, no console UI — so the window opens only after a manual DB change. Not low: when it does open it is up to 7 days of full admin access, including every restaurant's write history, with no way to cut a session short.

## convert-to-cod-leaves-upi-link-payable · LOW

**Where** `src/db/repos/dashboard.ts:108`  
**What** `convertToCod` flips `payment_method` to `cod` and `payment_status` to `unpaid`, but leaves every outstanding `payment` row at status `awaiting` and never cancels the gateway link. `attachPayment` (src/db/repos/orders.ts:327) does supersede outstanding `awaiting` rows — that was the M1 review #13 fix for the resend-link path — but the convert-to-COD path, which exists precisely because "the customer did not pay the UPI link, so the counter takes cash", was not covered by it. `markPaid` then honours the stale link: its only guards are `pay.status === 'paid'` and `current.paymentStatus === 'paid'`, neither of which a COD conversion sets.  

**Consequence** The customer is charged twice for one order with no refund path. Sequence a counter actually runs: order placed on UPI, link SMSed, customer does not pay, counter taps "Convert to COD", food handed over and cash taken — then the customer opens the older SMS and taps Pay. The gateway captures the money, `markPaid` marks the order `payment_status = 'paid'`, and the dashboard now shows a COD order as paid online while the till also holds the cash. This is the exact failure the M1 review #13 fix was written to close, reached through a different door.

**Verified** Real and reproduced: `convertToCod` leaves the order's `payment` row at `awaiting` and nothing cancels the gateway link, so a webhook for that link afterwards drives the order to `cod` + `paid` with cash already in the till. But the claim misplaces both the cause and the fix — the double *charge* happens at the gateway regardless of what the database does (the adapter has no `cancelLink`), and severity is low, not medium, because a Payment Link is dead 30 minutes after creation (Build Spec §9, enforced by the mock) and the outcome is a recorded, auditable payment row rather than a silent loss. The repo's own M1 review rated the identical exposure on the resend path (#13) low.

**Fix** Three separate changes, and the claim's middle one should not be made as written.

1. Database consistency (do this): inside `convertToCod`'s transaction, supersede the order's outstanding links exactly as `attachPayment` does — `tx.update(payment).set({ status: 'unpaid' }).where(and(eq(payment.orderId, orderId), eq(payment.status, 'awaiting'))).returning({ id: payment.id })` plus a `payment.supersede` audit row for each. `awaiting` then means what it says: money is expected on this link.

2. Do NOT have `markPaid` return `{ ok: false, reason: 'superseded' }` for a link whose order has moved to COD. That refuses to record money the gateway has already captured, leaving no payment row, no audit entry and no refund trail — strictly worse than today and a direct contradiction of `markPaid`'s own stated stance at orders.ts:417-419 ("the money is recorded and the dashboard shows it, and a refund is a human decision"). Keep recording it; add the missing *visible* signal instead — a board/detail flag for "COD order with a paid payment row: refund owed" — since `refunded` is currently an enum value nothing ever sets.

3. The only change that actually prevents the double charge is the unimplemented clause of M1 review #13: add `cancelLink(linkId)` to `PaymentsAdapter` (mock + razorpay) and call it wherever a link stops being the way this order gets paid — `convertToCod` and `attachPayment`'s supersede loop. Reopen #13 rather than filing this as a new dashboard.ts defect; both doors are the same missing capability.

4. Separate and worth fixing, as the claim notes at the end: `convertToCod` reads the order with no lock (`markPaid` locks the `payment` row, not `order`) and its UPDATE at dashboard.ts:114 has no compare-and-set, so a webhook committing between the read and the write is a lost update that flips a just-paid order back to `unpaid`. Add `eq(order.paymentStatus, before.paymentStatus)` to that `where` and let `firstRow`'s throw abort the transaction. (Not reproduced — PGlite is single-connection — but it follows from READ COMMITTED semantics and the absent row lock.)

## empty-assistant-turn-after-round-cap · LOW

**Where** `src/voice/loop.ts:351`  
**What** When a turn hits `MAX_TOOL_ROUNDS` with the model still asking for tools and saying nothing, the loop pushes `{ role: 'assistant', text: null, toolCalls: [] }` into `session.messages` and keeps it for the rest of the call. `toAnthropicMessages` maps that to `{ role: 'assistant', content: [] }`.  

**Consequence** Gemini tolerates the empty turn (I checked against the live key — it answered normally), so the primary provider is fine. Anthropic rejects a non-final message with empty content, so if `LLM_SECONDARY_PROVIDER=anthropic` is ever configured as the Build Spec §3 failover intends, a call that has hit the round cap once would fail over into a provider that 400s on every subsequent turn — four strikes and a `vendor_error` transfer, for a call that was otherwise healthy. NOT REPRODUCED against Anthropic: there is no Anthropic key in .env (`LLM_SECONDARY_PROVIDER=mock`), so this half is reasoning from the documented API constraint, not measurement.

**Verified** Real but latent: the round cap does leave a content-less assistant turn in `session.messages` for the rest of the call, and `toAnthropicMessages` maps it to `{role:'assistant',content:[]}`, which the Anthropic Messages API rejects on any non-final message — so the Build Spec's Anthropic failover would be dead for that call. Nothing in CLAUDE.md, the ADRs, the M2 design or the tests sanctions the empty turn; the comment directly above the push states the opposite intent ("a real provider refuses the next request..."). It stays low because it is unreachable in the shipped config (.env has `LLM_SECONDARY_PROVIDER=mock`) and Gemini, the primary, accepts it live. The claim's headline fix is wrong, though.

**Fix** Keep the assistant turn, give it content. In src/voice/loop.ts, where the response is recorded, use the line the caller actually hears rather than nothing:

  const calls = execute ? response.toolCalls : []
  const text = response.text ?? (calls.length === 0 ? lines.reask : null)
  session.messages.push({ role: 'assistant', text, toolCalls: calls })

(`lines` is already in scope in respond(), and `reply = reply ?? lines.reask` at the end means this is what was spoken, so the history stays truthful.) Do NOT use `if (response.text || execute) session.messages.push(...)`: omitting the message leaves a tool-result user turn immediately followed by the next turn's user turn, which the Anthropic mapping renders as two consecutive `user` messages and the API rejects for the same reason. A regression test belongs in src/voice/loop.test.ts asserting that no message in session.messages has null text and zero tool calls after a turn that hits MAX_TOOL_ROUNDS.

## orders-today-never-resets-at-midnight · LOW

**Where** `app/(restaurant)/app/(shell)/Board.tsx:53`  
**What** `todayCount` is seeded once from the server's `countOrdersSince(outlet.id, istDayStart(now))` and then only ever incremented by `merge()`. The board is server-rendered once and kept live by SSE; nothing re-renders it at the IST day boundary.  

**Consequence** A counter tablet left on overnight — which is what a counter tablet does — carries yesterday's total into today. Just after midnight the board and the all-done empty state say "27 orders today" when today has one. The number is the design §7.9 reassurance figure, so it quietly misreports the day's trade until someone reloads.

**Verified** Real, and not covered by any ADR, spec line or test: nothing in the mounted board tree reads the clock, so a tablet left open past IST midnight keeps yesterday's "N orders today" in the toolbar and in the all-done empty state. Severity low is right (display-only, self-heals on any client navigation or a full reload), but the claim's proposed `router.refresh()` fix is wrong — refresh preserves client state and `useState(ordersToday)` ignores the new prop, so the stale number would survive it.

**Fix** Keep the IST day the count belongs to on the client and reset on rollover — with a timer, not a refresh.

In `Board.tsx`, import `istDate`/`istDayStart` from `@/core/calendar.ts` (pure core, safe in a client component), hold `dayRef = useRef(istDate(new Date()))`, and add an effect that:
- arms `setTimeout` for `istDayStart(now).getTime() + 86_400_000 - Date.now()`, and on fire sets `todayCount` to 0, updates `dayRef`, and re-arms from the fresh clock;
- re-checks on `visibilitychange`/`focus` (a backgrounded or sleeping tablet throttles timers, so the timer alone can fire late or not at all) by comparing `istDate(new Date())` with `dayRef.current` and zeroing on mismatch;
- guards `merge()` the same way, so an arrival just after midnight starts the new day at `arrived` rather than adding to yesterday's total.

Optionally also pass `dayStart` from `page.tsx` so the client uses the server's notion of the day instead of deriving it, but do not rely on `router.refresh()` or a changed `ordersToday` prop to do the reset — neither re-seeds `useState`.

## duplicate-saved-addresses · LOW

**Where** `src/db/repos/customers.ts:216`  
**What** `saveAddress` always inserts, with no uniqueness check on (customerId, restaurantId, line1, pincode), and the address form (app/(customer)/r/[slug]/checkout/page.tsx:130-149) submits a server action with no disabled-while-pending state, so the same address is stored again every time it is typed or the button is double-tapped.  

**Consequence** A regular customer's "Saved addresses" list on the checkout fills with identical entries — they see the same flat listed twice, three times, and have no way to delete any of them. On a slow connection a single double-tap does it in one order. Build Spec §6 puts saved addresses first precisely so a repeat customer taps once; a wall of duplicates undoes that, and a later correction to one copy leaves the stale copies in the list.

**Verified** Real and reproduced: saveAddress inserts unconditionally, so identical (customerId, restaurantId, line1, area, pincode) input creates separate rows that listAddresses returns and the checkout renders as repeated "Deliver here" options, with no delete path anywhere. Nothing in CLAUDE.md, the ADRs or the existing tests sanctions it — the tests only save two different addresses.

**Fix** Fix in src/db/repos/customers.ts saveAddress, not in the form — the address-link and manual-order callers bypass the form entirely.

1. Before inserting, look for an existing row with the same customerId and restaurantId whose normalised line1 and pincode match, where normalised means lower(regexp_replace(trim(line1), '\s+', ' ', 'g')) — case and internal whitespace alone defeat a naive equality check (proved by the '12 mg road  ' row in the repro).
2. On a hit, update that row in place: fill in a landmark or label newly supplied, raise isConfirmed to true but never lower it, and return it. Write the audit as 'address.update' with the same redacted projection (id, customerId, restaurantId, label, area, pincode, source, isConfirmed) and the prior values as `before`. AuditEntry.action is a plain string (src/db/repos/ops.ts:27), so no enum change is needed.
3. Do NOT bump lastUsedAt on save, contrary to the claim's wording. lastUsedAt is the "last used" marker and src/db/repos/orders.ts:121,267 already set it when an order actually uses the address; writing it on a mere re-save would make a retyped address outrank one the customer actually ordered to, contradicting the documented ordering in listAddresses (customers.ts:198-201).
4. Optionally add a partial unique index on (customer_id, restaurant_id, lower(normalised line1), pincode) where pincode is not null, as a backstop for the concurrent double-submit, and treat its violation as a re-read of the existing row.

Defence in depth, not the fix: give the address, consent and "Send code" forms a small client submit button using useFormStatus with disabled={pending}, matching OtpForm.tsx:51 and ConfirmStep.tsx:201. The "Send code" point is accurate — src/auth/otp.ts:23 is createLimiter(5, 10 * 60 * 1000), so a double-tap burns two SMS and two of the five per ten minutes.
