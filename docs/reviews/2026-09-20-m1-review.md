# M1 review — 20 September 2026

> Two independent review passes over commit 2dd4531, after every Build Spec §14 M1 acceptance
> criterion had passed in a browser. Findings are reproduced as delivered; the fixes are in the
> commit that follows this file. Three findings were not acted on, with reasons, at the end.

## Spec fidelity and security

**HIGH**

1. **high** — `src/db/repos/customers.ts:80` (also `:228`, `src/db/repos/platform.ts:196`) — Every write to `customer`, `customer_address`, `staff_user`, `platform_user` and `outlet` goes through drizzle-orm 0.45, whose `DrizzleQueryError` message is `Failed query: <sql>\nparams: <values>`, so any driver failure (lock, connection drop, constraint race) throws an error whose message contains the phone number or full address, and the server actions that call these (`checkout/actions.ts:77,146`, `orders/new/actions.ts:122,141`, `restaurants/new/actions.ts:82`) let it escape to Next's server-side error log. Fix: in `src/db/client.ts` (or a `run()` helper in `repos/ops.ts`) catch `DrizzleQueryError` and rethrow a sanitised error that keeps `cause.code`/`constraint` and drops `query`/`params`; `createRestaurantAction:102` must stop returning `e.message` verbatim.

2. **high** — `app/(restaurant)/app/(shell)/menu/actions.ts:15` — `setAvailability` toggles any `menu_item` uuid with no check that it belongs to the session's outlet, and item uuids are public (they ship to every browser that opens `/r/{slug}`), so a staff login at restaurant A can mark restaurant B's whole menu sold out. Fix: load `getPublishedMenu(outlet.id)` and refuse unless `menu.items.some(i => i.id === itemId)`, exactly as `saveItem:126-128` already does.

**MEDIUM**

3. **medium** — `app/(restaurant)/app/(shell)/orders/new/actions.ts:164` — A manual order is written with `customer_id` set whenever a phone is typed, regardless of consent (only the `customer_restaurant` bump at `:194` is gated), which violates Build Spec §7 ("links the order to a profile *if consent exists*") and §10, and inflates the §12 profile-capture metric. Fix: set `customerId` on `createOrder` only when `mayStoreProfile` is true; keep the phone-only `customer` row for the UPI link but leave the order unlinked.

4. **medium** — `app/(customer)/r/[slug]/checkout/actions.ts:186-193` — `placeOrderAction` checks only for a session, not for live `order_fulfilment` consent, so a customer who withdrew consent (status-page one-tap) with an old checkout tab open, or anyone calling the action directly, places an order linked to their `customer_id` and saved address with no valid consent; the design says validation sits at the trust boundary, and here the only gate is the page. Fix: after `requireCustomer()`, load `getConsent` and return `{ ok:false, reason:'consent_required' }` unless `hasValidConsent(view, 'order_fulfilment')`.

5. **medium** — `app/api/v1/webhooks/razorpay/route.ts:36-44` — `stripContact` deletes only `payload.payment.entity.contact/email`, but a real `payment_link.paid` event also carries `payload.payment_link.entity.customer.{contact,email,name}` and `payload.payment.entity.vpa` (for UPI, routinely `<mobile>@upi`) and `.notes`, so the phone number lands verbatim in `payment.webhook_payload`, a table outside the four allowed. Fix: strip `payment_link.entity.customer`, `payment.entity.vpa`, `payment.entity.notes` and `payment.entity.card`/`email` as well, or store only an allow-listed projection of the event.

6. **medium** — `src/auth/secrets.ts:17-24` — When `SESSION_SECRET`/`PHONE_HASH_PEPPER` are unset and `NODE_ENV !== 'production'` the code warns and uses `sha256("serveline-dev-only:…")`, a value anyone can compute from the repo, so any reachable non-production deployment (staging on `next dev`, `NODE_ENV=staging`) lets an attacker mint an `sl_platform` cookie with `role: 'admin'` and forge OTP challenges; CLAUDE.md says a missing variable is an error, never a fallback. Fix: throw unless an explicit opt-in such as `ALLOW_DEV_SECRETS=1` is set, and never derive the value from a constant string.

7. **medium** — `app/(customer)/r/[slug]/lib.ts:14-19` and `app/(restaurant)/app/_lib/session.ts:13-21` — The admin-only "Suspend restaurant" action (Build Spec §8) changes `restaurant.status` and nothing else: `loadRestaurant` still serves the ordering page, `placeOrder` still takes money, and `currentOutlet` still admits staff, so suspension is a label with no effect. Fix: in `loadRestaurant` render the closed screen when `restaurant.status === 'suspended'` (and refuse in `placeOrder`), and in `currentOutlet` redirect suspended restaurants to a "contact ServeLine" page.

8. **medium** — `app/(restaurant)/app/(shell)/MondayNag.tsx:13-19` — The quick-pick chips write fabricated midpoints into `external_order_count` (`"50+"` stores 75, `"26–50"` stores 38), so a restaurant doing 300 Swiggy orders a week records 75 and the North Star (Direct Order Share, Ideation §9, "two numbers a week") is overstated several-fold as if it were exact. Fix: either drop the chips and require the exact number, or store the chosen range (`min`/`max` columns) and compute the share from the range's upper bound; do not persist an invented point value.

9. **medium** — `src/auth/otp.ts:23,55` — The OTP issue limiter allows 5 requests per 10 minutes per IP, and table-QR diners on the restaurant's Wi-Fi (or Jio CGNAT) share one public IP, so the sixth diner in ten minutes at a busy dinner gets "Too many attempts" and cannot order. Fix: raise the per-IP window to something like 60 per 10 minutes (keep 5 per phone), or key the IP limit on `ip + phoneHash` and reserve the pure-IP limit for a much higher abuse threshold.

**LOW**

10. **low** — `app/(restaurant)/app/(shell)/orders/new/actions.ts:44-45` — `lookupCustomer` returns `found: true` from the platform-wide `customer` table before the restaurant-scoped consent check, so any staff login can test whether a phone number has ever used *any* ServeLine restaurant, which crosses restaurants without consent (Build Spec §4). Fix: derive `found` from `getCustomerRestaurant(customer.id, restaurant.id)` being non-null, and rate-limit the action per staff user.

11. **low** — `app/(customer)/r/[slug]/address/[token]/actions.ts:74` — Confirming an address mints a 30-day customer session from a 7-day bearer token that travels in a URL (SMS, browser history, proxy logs), which Build Spec §6 does not ask for; nothing mints the token at M1, but the endpoint is live. Fix: do not call `createSession` here; redirect to the status page with the token as a one-shot read, or require the OTP step for a session.

12. **low** — `src/checkout/place-order.ts:183-186` — COD and zero-total orders are moved `received → confirmed` automatically, so the counter never sees the "Accept" step the board offers for every other `received` order; the code itself calls this "the task's reading" and neither the Ideation file nor Build Spec §6 decides it. Fix: leave COD orders at `received` (the UPI branch confirms via webhook because payment is the acceptance) and record the decision in the Ideation file if auto-confirm is wanted.

13. **low** — `app/(restaurant)/app/(shell)/board-actions.ts:105-111` — "Resend payment link" creates a second live link while the first (30-minute) link is still payable and nothing cancels it, so a customer who taps both SMS messages is charged twice with no refund path. Fix: add `cancelLink(linkId)` to the payments adapter, cancel every `awaiting` payment row for the order before attaching the new one, and have `markPaid` refuse a link whose order is already `paid`.

14. **low** — `src/db/seed.ts:321` — The seed writes the full `customer_address` row (line1, landmark) into `audit_log.after`, which CLAUDE.md and `writeAudit`'s own contract forbid and which the admin audit page then displays. Fix: audit the same redacted projection `saveAddress` uses (id, customerId, restaurantId, label, area, pincode, source, isConfirmed).

**Count: 2 high, 7 medium, 5 low.**

## Design fidelity

**Design-fidelity review — ServeLine M1** (contract: `docs/design/steel-and-enamel.md`)

**MEDIUM**

1. **Counter targets under 56px on the dashboard (§6.1)** — `app/(restaurant)/app/(shell)/Board.tsx:216,225,233,235`, `MondayNag.tsx:54`, `menu/page.tsx:44`, `(shell)/layout.tsx:39`, `src/ui/OrderCard.module.css:136`. The "Seen" acknowledgement on the new-order band, "Retry now" on the offline band, "Tap to enable order sounds"/"Sound off", the nag's "Reopen", "Add item" and "Sign out" are all `size="dense"` (32px) on the counter surface, and the OrderCard lean-in expand row is `min-height: var(--touch-min)` (44px); the screenshot also shows the sound button as a filled `primary` plate in the top-right corner competing with the card primaries (§6.2). Fix: use `size="counter"` for every button on the restaurant surface (the Band's `action` slot can hold a 56px ghost), make the sound toggle `ghost`, and set `.leanIn { min-height: var(--touch-counter) }`.

2. **Focus ring invisible on the quantity stepper (§9 "never remove the ring")** — `src/ui/QtyStepper.module.css:19` (`.stepper { overflow: hidden }`) and `:61` (`.input { outline: none }`). The global `:focus-visible` ring is a 4px outer `box-shadow`; the three controls fill the stepper's box, so the parent's `overflow: hidden` clips the ring on all sides and keyboard focus on −/qty/+ is not visible. Fix: remove `overflow: hidden` from `.stepper` (round the first/last `.btn` corners instead) and delete `outline: none`.

3. **Customer "Have a code?" form is squashed to the right edge** — `app/(customer)/r/[slug]/customer.module.css:79-94` and `page.tsx:94`. `.codeForm` shares the element with `.toolbar`, inherits `flex-direction: column`, and its `align-items: flex-end` then shrinks the field to intrinsic width and right-aligns it with "Apply" underneath (visible in `docs/screenshots/m1/ordering-page.png`); on a 360px phone the code input is a narrow right-hugging box. Fix: add `flex-direction: row` to `.codeForm`.

**LOW**

4. **Hindi "orders today" line renders as a bare number** — `Board.tsx:231`. The count is extracted by `t('empty.allDone').split('.')`, but the Hindi string ends sentences with danda (।), so the split yields nothing and the fallback prints just `8`. Fix: add a dedicated `board.ordersToday` key in all three languages and stop slicing a translated sentence.

5. **Assertive live regions used for validation errors (§9: one assertive region product-wide)** — `MenuClient.tsx:289`, `checkout/page.tsx:92,133`, `address/[token]/page.tsx:72`, `cards/BatchForm.tsx:26` use `role="alert"`. Fix: use `role="status"` (or nothing — `Field` already wires `aria-describedby`); reserve `role="alert"` for the new-order Band.

6. **Print card clips Indic names and hard-codes steel hex (§4.2 rule 4, §11.11, token rule)** — `cards/[batchId]/print/print.module.css:20-21,29,34,50`. `.text { line-height: 1.3 }` applies to the restaurant name (user content) inside a fixed 55mm card, and `#fff`, `#192227`, `#4f5e68`, `font-weight: 700` are covered by `--steel-000/900/600` and `--fw-bold`. Fix: `line-height: var(--lh-ui)` on `.name`/`.offer`, and reference the raw steel step tokens (print is forced light, so the step tokens rather than role tokens are correct).

7. **Favicon uses the received-state blue as decoration (§3.2 palette law, §11.3)** — `app/icon.svg:1` paints the edge `#0B5FA5`. Fix: draw the icon in steel only (e.g. the edge in `#85949E`, the neutral edge the design uses for the Monday nag).

8. **`aria-label` overrides the visible text on two controls** — `src/ui/OrderCard.tsx:204` (lean-in row is announced as "Show items", losing "3 items · ₹640 · Paid") and `src/ui/QtyStepper.tsx:71` (number button announced as "Quantity", losing the value). Fix: drop the `aria-label` on the lean-in button and use `aria-expanded` + visible text, and name the qty button `${t('qty.label')} ${qty}`.

9. **Hard-coded English inside trilingual pages / missing `lang`** — `app/(customer)/r/[slug]/page.tsx:124-125` and `order/[orderId]/page.tsx:75` render "TABLE"/"DELIVERY" as English uppercase on a Hindi/Kannada customer page although `checkout.table` exists in `i18n.ts:87`; `settings/SettingsForm.tsx:71` renders "हिन्दी"/"ಕನ್ನಡ" without `lang` on an English form (the `<select>` in `settings/page.tsx:57` does it right). Fix: use `t('checkout.table')` / a translated delivery label, and add `lang={l}` to the checkbox labels.

10. **Expired payment link is a dead end (§7.10.4)** — `order/[orderId]/page.tsx:79-83` keeps offering "Pay now" while the link is `awaiting`; `mock/pay/[linkId]/page.tsx:47-51` then shows only "This link has expired" + "Back", looping the diner with no "Try again" or "Pay at the counter". Fix: on the status page, when the pending link is past `expiresAt`, show the §7.10.4 screen with a re-issue action and a `tel:` "Pay at the counter" fallback.

11. **Operator-facing copy cites an internal document (§7.10 copy rules)** — `menu/page.tsx:22` "…The agent console publishes the first one (Build Spec §8)." Fix: say what to do ("Ask ServeLine to publish your first menu") and drop the citation.

**Count: high 0 · medium 3 · low 8**

## Not acted on

- **SEC-12 (COD auto-confirm bypasses Accept).** Build Spec §5.2 decides it: "cash on delivery (order
  goes to confirmed immediately if outlet.cod_enabled)". The behaviour matches the spec.
- **SEC-11 (address-link token mints a 30-day session).** Nothing mints that token until M2's voice
  flow exists; the session length is decided with that flow, not before it.
- **SEC-8 (nag chips store midpoints)** — acted on differently from the suggested fix: the chips now
  fill the exact field so the operator sees and can correct the number before Save; only the field's
  value is stored. The range's ease is kept without inventing a hidden point value.
